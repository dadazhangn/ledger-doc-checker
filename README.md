# 台账核对 · Ledger Check

一个独立运行的本地工具：以选定的 Excel 台账为基准，核对多份 Word 的固定字段与普通明细表，展示两边的原值及位置。

当前为 **0.1.0 演示验证版**。可以运行、配置和导出报告，尚未通过真实业务模板验收。仓库演示文件全部为虚构数据，不是实际项目资料或实际执行记录。

![本地核对界面](docs/images/overview.png)

## 运行

建议使用 Node.js 22 或 24。当前开发机也已在 Node.js 20.17.0 完成构建与测试。

在项目目录执行：

```sh
npm ci
npm run build
npm start
```

浏览器打开终端显示的本机地址，默认是 `http://127.0.0.1:4173`。端口被占用时，可设置 `LEDGER_CHECK_PORT` 为其他端口；设为 `0` 由系统分配。

首次可以点击 **体验演示**。源码附带 `examples/` 下的 Excel、两份 Word 和一份方案。需要重新生成演示文件时运行 `npm run demo:generate`；该命令只重建演示目录内约定的四个文件。

## 一次核对如何完成

1. 选择一份 `.xlsx` 和 1–30 份 `.docx`，点击“读取资料”。
2. 选择对象工作表、表头行、对象关联列，并指定 Word 中的对象字段标签。
3. 为每份 Word 明确选择对应的台账对象。一个对象可以对应多份文档；每份文档都必须与自己的对象字段精确对应。
4. 添加固定字段映射，选择比较规则。需要明细核对时，再指定明细工作表、所属对象列、条目唯一键和比较列。
5. 点击“开始核对”，查看差异、无法核对项和来源；需要时导出 HTML 或 JSON。
6. 保存方案，下一批同结构资料可以重新导入该方案，再确认文档对应关系。

核对使用用户选中的文件内容，不递归扫描目录。上传内容只进入本机服务内存，不保存上传副本，也不向模型或外部服务发送业务文件。关闭服务会清除内存任务；导出的方案和报告由用户自行保管。首次安装依赖需要联网。

## 首版支持什么

| 范围 | 规则 |
| --- | --- |
| 对象关联 | 台账中唯一关联键 + Word 中明确标签；多候选、重复键和错绑会提示，禁止自动取第一条 |
| Word 固定字段 | 普通表格里的标签与相邻值，或正文的“标签：值”段落；同一标签多处命中时保留歧义 |
| 明细表 | 第一行为表头，通过配置的列名唯一定位表格；按唯一条目键匹配，检查缺项、多项、重复和值 |
| 文本 | 原文精确比较；可明确选择只去除首尾空白。保留大小写和文本编号的前导零 |
| 日期 | 明确的年/月/日，例如 `2026-11-01`、`2026/11/1`、`2026年11月1日` |
| 数字 | 十进制定点数与非负容差；不自动推断单位、百分比、千分位或科学计数法 |
| 来源 | Excel 工作表与单元格；Word 正文段落或表格行列。不会推算真实页码 |
| 公式 | 默认无法核对；可显式允许采用已保存的缓存值，报告保留“未重算、缓存时效未知”的提示 |

对象表和明细表从选定表头行后开始读取，包括隐藏和筛选掉的行。明细检查覆盖该对象的全部来源明细；首版没有针对同一对象不同文档的明细子集筛选功能。

Word 页眉页脚、文本框、图片/OCR、嵌套表格、纵向合并表格、未处理修订和域代码均不能作为已验证数据。复杂格式会产生无法核对项或范围提示。Excel 仅对纯零掩码（如 `0000`）保留数字显示的前导零，其他自定义数字格式不承诺复现其显示样式；作为文本编号使用的列建议在 Excel 中保存为文本。

## 结果含义

- **一致**：该项按选定规则比较一致。
- **差异**：该项有明确不一致、必填空值、明细缺项或多项。
- **无法核对**：字段未定位、关联有歧义、格式不支持，或无法可靠读取来源值。
- **检查未完成**：仍存在无法核对项或文件错误；已找到的差异也会一并保留。

只有配置范围内全部检查完成且没有差异时，才显示“配置范围内一致”。结论不代表整份文档已经正确、业务数据真实，或所有内容都被覆盖。

报告记录文件 SHA-256、规范化方案及其 SHA-256、引擎版本。相同输入与方案可复现核对结果。界面里更换文件或修改方案后，旧结果会标记过期并暂停导出；工具不监控用户在 Word/Excel 中另行编辑磁盘文件，修改后必须重新选择并读取文件。

## 演示应当得到什么结果

| 人为设置的演示差异 | 台账 | Word |
| --- | --- | --- |
| 演示对象甲的版本 | 1.0 | 1.1 |
| 演示对象甲 / 演示条目乙的数量 | 5 | 6 |
| 演示对象甲的附加条目 | 不存在 | 演示附加项 |
| 演示对象乙的一个条目 | 演示条目丙 | 缺失 |

预置方案的结果应为：**10 项一致、4 处差异、0 项无法核对、0 个文件错误**。Word 中的部分文字被拆成多个格式片段，明细顺序也与台账不同，用于验证这些变化不会引入额外误报。

## 限制与运行边界

- 单文件最多 12 MB，每批合计最多 48 MB，最多 30 份 Word。
- Excel 最多 20 张表、每表含表头 10,001 行和 100 列、总计 250,000 个非空单元格。
- Office ZIP 最多 4,000 个条目、实际解压合计 80 MB；读取的 Word XML 每部分最多 8 MB。
- 单任务在工作线程运行，可取消；60 秒仍未完成会停止并提示失败。
- 潜在检查项保守估算超过 100,000 时要求分批，避免生成过大报告。
- 服务只监听本机回环地址，不适合部署成多人共享的服务器。

这些是输入与资源限制，尚不是性能或准确率承诺。是否实用，需要继续以真实模板检查误报、未完成项和总耗时。

## 开发与验证

```sh
npm test
npx playwright install chromium
npm run test:ui
```

也可以将 `PLAYWRIGHT_EXECUTABLE_PATH` 指向测试用浏览器程序。自动化使用临时浏览器上下文，不复用日常浏览器资料。

结构：`src/parsers.ts` 负责可追溯解析，`src/engine.ts` 负责方案与确定性比较，`src/server.ts` 提供本机服务和可取消任务，`public/` 提供界面。引擎可脱离界面使用，也不依赖 DSH。
